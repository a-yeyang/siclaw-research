SKILL: Diagnosing network-dns connectivity and DNS-resolution failures

WHEN TO APPLY
A client pod is unable to resolve or reach a Service even though the corresponding server pod exists and is Running. Treat those pod crashes and restarts as symptoms, not the root cause. Root causes in Kubernetes almost always reside within controllable layers, and you must positively rule each in or out before identifying the exact issue.

PRECISE ORDER OF READ-ONLY CHECKS
1. ENUMERATE ALL NETWORKPOLICIES IN THE NAMESPACE.
   - List all network policies using `kubectl get networkpolicy -n <your-namespace>`
   - Describe each policy for details (`describe networkpolicy <policy-name>`).
   - Compare the policy’s selector labels against the client pod labels (`kubectl get pod <client-pod> -l app=<client-app-name> -n <namespace> -o yaml`).
   - Verify if any policy denies egress from the client to DNS servers (UDP port 53) or ingress to the server.

2. VERIFY CLIENT DNS CONFIGURATION.
   - Check the client pod’s DNS configuration (`kubectl get pod <client-pod> -o yaml`).
   - Ensure there are no custom DNS server overrides specified in the dnsConfig section.
   - Confirm the dnsPolicy is set to "NamespaceLocal" or "ClusterFirst".

3. INSPECT SERVICE DEFINITION AND PROXY CONFIG.
   - Examine the service manifest definition (`kubectl get svc <service-name> -o yaml`) for annotations or selector mismatches.
   - Look for any custom DNS or proxy configurations (e.g., NodePortServices with exposed DNS services).

RECOGNIZING THE ROOT CAUSE
The precise root cause could manifest as:
- Denial of Service traffic for DNS from/to the client via NetworkPolicies.
- Incorrectly configured DNS settings on the client pod.
- Misconfigured service definitions leading to DNS resolution issues.
- Inadequate DNS proxy configurations disrupting DNS lookup paths.

CORRECT FINAL DIAGNOSIS
Your correct diagnosis must detail:
- The exact resource involved (pod/service/node/networkPolicy).
- The specific mechanism causing the issue (NetworkPolicy deny, incorrect DNS config).
- The scope affected (single pod/service, entire namespace).
- Supporting evidence from logs, network traces, and inspection results.
- A remediation step (update policy, change DNS config, reconfigure service).

SAFE REMEDIATION ACTION
To fix the issue, take the following steps based on your diagnosis:
- Modify the NetworkPolicy selector to allow necessary traffic if denied.
- Update the client pod’s DNS configuration if misconfigured.
- Adjust service definitions or proxy configurations if mismanaged.
- Validate changes with another attempt to access the service.

REVIEW & MONITOR
After implementing a remediation, verify the issue has been resolved by retrying the client pod’s interaction with the service. Monitor for continued stability and adjust further if needed.
