## Diagnosis: Pod `c014-crash` — CrashLoopBackOff

### Root Cause

The container command exits immediately with a non-zero exit code:

```
sh -c "echo 'checkpoint /models/ckpt.pt not found'; exit 44"
```

The container prints `checkpoint /models/ckpt.pt not found` and then **exits with code 44** (`exit 44`). Since the pod's `restartPolicy` is `Always`, Kubernetes repeatedly restarts it — but the command always fails at startup, so it never becomes Ready (CrashLoopBackOff).

### Evidence

1. **Pod YAML** (`kubectl get pod -o yaml`): The container's command is literally `exit 44` after printing a "file not found" message — a code-level exit, not a runtime issue.
2. **Exit codes in status**: Every termination shows `exitCode: 44`, `reason: Error`.
3. **Logs**: `checkpoint /models/ckpt.pt not found` — no image pull error, no OOM, no dependency issue.
4. **182 restarts over 15h** with a back-off now at 5 minutes: the container has never succeeded even once.

The container is crashing by design — it's a training entrypoint that exits when its checkpoint file is missing, and uses `exit 44` (a custom code, not a system signal).

### Impact & Scope

- **Isolated to this pod** — no cluster-wide impact.
- The pod has been down for 15 hours, 0/1 Ready.

### Confidence: **High** — the root cause is in the literal container command.

### Remediation (safe, read-only suggestion)

The fix depends on intent:

- **If the checkpoint was supposed to exist**: The workload needs the checkpoint `/models/ckpt.pt` pre-populated (e.g. via an init container or a PVC mount) before the `trainer` container starts.
- **If `exit 44` is a placeholder**: Replace the command with one that either creates/stubs the checkpoint file or removes the fatal exit, e.g.:
  ```yaml
  command: ["sh", "-c", "touch /models/ckpt.pt && echo 'checkpoint created, starting training...'; <actual-training-cmd>"]
  ```
- **If this is a training job**: Consider a `Job` (not a pod with `restartPolicy: Always`) so the failure is reported once rather than cycling forever.
