## Diagnosis: c100 — Compound GPU Runtime Incident

### Root Cause 1: Non-existent Scheduler — Pod Permanently Stuck in Pending

- `kube-scheduler` (via HA control plane pods)
- `volcano-scheduler` (running in `volcano-system`)

Neither is named `gpu-scheduler-profile-missing`. Because Kubernetes only assigns a pod to a node when the named scheduler processes it, and this scheduler doesn't exist, the pod is permanently stuck in `Pending` with `Node: <none>` and zero scheduling events.

**Impact:** The pod will never be scheduled. It is indefinitely blocked.  
**Confidence:** High (directly confirmed from `spec.schedulerName` and scheduler inventory).

### Root Cause 2: NCCL Network Interface Misconfiguration (Application-level)

**Evidence:** Container command:
```
sh -c "echo 'NCCL_SOCKET_IFNAME=eth9 not found'; exit 45"
```
`restartPolicy: Always`

The trainer container is hardcoded to emit `NCCL_SOCKET_IFNAME=eth9 not found` and exit with code 45. Exit code 45 is not a standard NCCL error code but signals a fatal custom/application-level failure. The referenced interface `eth9` does not exist in typical pod environments (RDMA/RoCE secondary interfaces are typically `net1`, `eth0`, etc.). `restartPolicy: Always` means that even if the scheduler issue were fixed and the pod were scheduled, it would immediately crash and enter `CrashLoopBackOff` — it would never succeed.

**Impact:** Even after resolving the scheduler, the container will crash-loop indefinitely due to a missing/misconfigured NCCL network interface.  
**Confidence:** High (command is deterministic and always exits non-zero).
